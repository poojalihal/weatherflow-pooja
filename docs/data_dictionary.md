# WeatherFlow Data Dictionary

## Dataset Overview

- **Source:** Open-Meteo Forecast API
- **Source URL:** https://api.open-meteo.com/v1/forecast
- **Licence:** CC BY 4.0
- **Database:** SQLite (`weather.db`)
- **Table:** `weather_hourly`
- **Refresh frequency:** On each manual or scheduled pipeline execution
- **Grain:** One row per city per hourly observation timestamp
- **Cities:** Birmingham, Cardiff, Edinburgh, London and Manchester
- **Canonical timezone:** UTC
- **Local timezone:** Europe/London
- **Number of columns:** 10
- **Records per city per successful extraction:** 48
- **Records processed per complete pipeline run:** 240
- **Composite primary key:** `(city, observed_at_utc)`

The total number of stored records increases as new hourly observation timestamps are collected. Overlapping records are replaced rather than duplicated.

## Primary Key and Constraints

The `weather_hourly` table uses the following composite primary key:

```sql
PRIMARY KEY (city, observed_at_utc)
```

The combination of city and UTC observation timestamp uniquely identifies each weather record.

The following columns have a `NOT NULL` constraint:

- `city`
- `observed_at_utc`
- `observed_at_local`
- `ingested_at_utc`

Weather measurement columns are nullable because the source API may return missing values.

The pipeline uses `INSERT OR REPLACE` to prevent duplicate primary keys when overlapping weather records are processed.

## Timestamp Handling

Weather observation timestamps are requested from the Open-Meteo API in UTC.

During transformation, the pipeline:

1. Converts API timestamps into timezone-aware UTC datetime values.
2. Stores the canonical timestamp in `observed_at_utc`.
3. Converts UTC timestamps to the `Europe/London` timezone.
4. Stores the UK local timestamp in `observed_at_local`.
5. Generates a UTC ingestion timestamp in `ingested_at_utc`.

All three timestamp columns are stored as ISO 8601 text values with explicit timezone offsets.

### Daylight Saving Time Examples

| Season | UTC Timestamp | UK Local Timestamp |
|---|---|---|
| Winter (GMT) | `2026-11-23T12:00:00+00:00` | `2026-11-23T12:00:00+00:00` |
| Summer (BST) | `2026-07-15T12:00:00+00:00` | `2026-07-15T13:00:00+01:00` |

UTC timestamps are used for record identification, ordering and duplicate detection.

UK local timestamps are available for business analysis based on local calendar dates.

## Additional Notes

- Weather measurements originate from the Open-Meteo hourly response.
- Measurement units are available in the `hourly_units` object of the raw JSON response.
- `weather_code` follows the WMO weather interpretation code system.
- SQLite uses TEXT storage for ISO 8601 timestamps, REAL for decimal measurements and INTEGER for integer measurements.
- Raw API responses are preserved under `data/raw/`.
- The final SQLite schema differs from the exploratory dataset used in the Week 1 Jupyter notebook.
- Dataset size and observation coverage change as additional pipeline executions are completed.
- Nullable indicates whether the database schema permits missing values; it does not indicate that missing values are currently present.

### Beaufort Scale

Lower boundaries are inclusive.

| Beaufort force | Minimum wind speed (m/s) |
|---:|---:|
| 0 | 0.0 |
| 1 | 0.3 |
| 2 | 1.6 |
| 3 | 3.4 |
| 4 | 5.5 |
| 5 | 8.0 |
| 6 | 10.8 |
| 7 | 13.9 |
| 8 | 17.2 |
| 9 | 20.8 |
| 10 | 24.5 |
| 11 | 28.5 |
| 12 | 32.7 |

Negative or missing wind speeds produce a null Beaufort value.

### Outdoor Work Risk

High-risk conditions take priority over medium-risk conditions.

- High: Beaufort >= 7, weather category is storm or snow,
  or precipitation >= 4 mm.
- Medium: Beaufort >= 5, precipitation >= 1 mm,
  or temperature <= 0 degrees Celsius,
  provided no high-risk condition applies.
- Low: none of the above conditions applies.

These are programme-defined business classification rules.
Formal data quality validation will be added in Task 2.4.

### Weather Code Reference

"unknown". Missing daylight information remains null.

## Week 2 — Data Quality and Quarantine (Task 2.4)

| Column | Type | Definition |
|---|---|---|
| dq_failure_reason | String | Semicolon-separated validation check names explaining why a record was quarantined |

The dq_failure_reason column is present only in quarantined
records.

Quarantined records retain their original transformed values
for investigation and possible reprocessing.

Data quality thresholds are configured in config.yaml.

Dataset-level uniqueness is evaluated using:

city, observed_at_utc, source

Expected hourly coverage is checked against the requested
UTC observation window for every configured city.

Quarantine and warning counts can overlap across checks
because a single record may fail more than one check.

The final number of quarantined rows counts each rejected
record only once.

The data quality report records check outcomes and pipeline
loading results for each execution.
